# File Handling — Assumptions and Limitations

> **TL;DR** — All uploads are fully loaded into RAM before hitting MinIO (no streaming). The hybrid parser writes a temp file because pymupdf4llm requires a file path. Peak RAM during parsing is ~5–8× file size. On an 8 GB machine, keep PDFs under ~15 MB for the hybrid pipeline. Several temp/local files are not cleaned up after use — see known limitations below.

## Assumptions

| #   | Assumption                                                                                                                                                                                                                                                            | Limitation it introduces                                                                                                                                                                                                                                                                      |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | **Entire uploaded file fits in memory.** All upload endpoints (`/upload`, `/ingest-file`, `/ingest-files`) call `await file.read()`, loading the complete file into RAM before forwarding to MinIO.                                                                   | On a basic machine (8 GB RAM, ~4 GB available), the practical upload ceiling is ~1 GB per file. Multiple concurrent uploads compound this — e.g. 5 × 200 MB uploads consume ~1 GB simultaneously. FastAPI's `UploadFile.file` (a `SpooledTemporaryFile`) is never streamed directly to MinIO. |
| 2   | **`pymupdf4llm` requires a file path.** Both V1 and V2 parsing pipelines write a temp file to disk because `pymupdf4llm.to_markdown()` does not accept an in-memory stream or bytes object.                                                                           | Even when the PDF is already in memory (V2 downloads bytes from MinIO), a redundant disk write is unavoidable. This adds I/O latency and means temp file cleanup is required in a `finally` block. If the process crashes between write and cleanup, orphaned temp files remain on disk.      |
| 3   | **V2 pipeline holds the full PDF in memory for the entire function.** `pdf_bytes` is downloaded once and kept alive so that `pymupdf.open(stream=...)`, `pymupdf4llm`, and `DocumentStream(stream=BytesIO(pdf_bytes))` can all reference it.                          | Peak RAM for V2 is ~5–8× the file size (original bytes + pymupdf internal copy + pymupdf4llm markdown + Docling's BytesIO copy). Combined with Docling's ML models (~500 MB–1 GB), a basic 8 GB machine can only process PDFs up to ~10–15 MB / 80 pages before risking OOM.                  |
| 4   | **Page rendering processes all pages at once.** V1 iterates over every page calling `page.get_pixmap()`, saves each PNG to disk, and uploads to MinIO — one by one but without freeing the pixmap before the next iteration's disk I/O completes.                     | Each uncompressed pixmap is ~10–30 MB. For a 200-page PDF, pixmap + PNG disk writes can spike memory and disk usage. There is no batching or back-pressure mechanism to cap concurrent resource use.                                                                                          |
| 5   | **`upload_corpus_documents` writes a temp file unnecessarily.** The endpoint reads file bytes with `await file.read()`, writes them to a temp file, then calls `upload_file(file_path=...)` — even though `upload_bytes(data=...)` could upload directly from memory. | Extra disk I/O (write + delete) per file with no benefit. The `ingest-file` and `ingest-files` endpoints already use `upload_bytes()` correctly, making this an inconsistency.                                                                                                                |
| 6   | **Downloads use `FileResponse` with temp files.** Both `/download` and `/images/download` download the object from MinIO to a temp file, then serve it via FastAPI's `FileResponse`.                                                                                  | Temp files are never cleaned up after the response is sent (acknowledged by a TODO in the code). Over time this leaks disk space. Switching to `StreamingResponse` with MinIO's raw stream would eliminate temp files entirely and reduce time-to-first-byte.                                 |
| 7   | **Report generation writes to a local file before uploading.** `generate_markdown_report()` writes the markdown to a local `.md` file, then uploads it to MinIO via `upload_file()`.                                                                                  | The local file is never deleted after upload, leaking disk space. The report could be assembled as a string in memory and uploaded via `upload_bytes()` since reports are small (KB-range).                                                                                                   |
| 8   | **V1 image extraction writes to a shared `parsed_images/` directory.** `pymupdf4llm` with `write_images=True` writes extracted images to a single hardcoded directory, which is later cleaned up with `shutil.rmtree()`.                                              | If two ingestion tasks run concurrently, they share the same `parsed_images/` directory, risking file collisions or one task deleting another's images mid-processing. The directory is not scoped per `doc_id`.                                                                              |
| 9   | **Docling ML models are loaded per invocation.** The V2 pipeline imports and instantiates `DocumentConverter` inside the function body on every call.                                                                                                                 | Docling model loading adds ~500 MB–1 GB of RAM and significant startup latency per document. Models are not cached or shared across invocations.                                                                                                                                              |

## Limitations — Maximum File Sizes (8 GB RAM, basic config)

| Endpoint / Pipeline                           | Bottleneck                                         |     |
| --------------------------------------------- | -------------------------------------------------- | --- |
| `POST /corpus/document/upload`                | `await file.read()` loads entire file into RAM     |     |
| `POST /corpus/document/ingest-file`           | Upload (in-memory) + parsing pipeline              |     |
| `POST /corpus/document/ingest-files`          | `await file.read()` per file, sequential           |     |
| V1 pipeline (`process_document_for_tasks`)    | Pixmap rendering + pymupdf4llm markdown            |     |
| V2 pipeline (`process_document_for_tasks_v2`) | Multiple in-memory copies + Docling models         |     |
| `GET .../download`                            | Disk-based `FileResponse` (streams from temp file) |     |
| `GET .../images/download`                     | Disk-based `FileResponse`                          |     |
| `generate_markdown_report`                    | String assembly in memory                          |     |

## Possible Optimizations

| #   | Optimization                                                                                                                         | Where it applies                | Expected impact                                                                                      |
| --- | ------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------- | ---------------------------------------------------------------------------------------------------- |
| 1   | **Stream `UploadFile.file` directly to MinIO** via `put_object(file.file, size)` instead of `await file.read()`.                     | Upload + ingest endpoints       | RAM per upload drops from 1× file size to ~1 MB. Multi-file batches scale to disk, not RAM.          |
| 2   | **Use `upload_bytes()` in `upload_corpus_documents`** to match `ingest-file`/`ingest-files`.                                         | `/corpus/document/upload`       | Eliminates unnecessary temp file disk I/O.                                                           |
| 3   | **Release `pdf_bytes` early in V2** after the temp file is written and `pymupdf.open()` is done. Re-read from temp file for Docling. | `process_document_for_tasks_v2` | Frees ~1× file size of RAM before Docling runs. Max file size increases from ~10–15 MB to ~25–30 MB. |
| 4   | **Batch page rendering** (e.g. 20 pages at a time) with immediate `del pix, png_bytes` after each upload.                            | V1 page pixmap loop             | Caps pixmap memory at ~20 pages instead of unbounded.                                                |
| 5   | **Replace `FileResponse` with `StreamingResponse`** using MinIO's raw `get_object()` stream.                                         | Download endpoints              | Zero temp files, zero disk leak, immediate first-byte delivery.                                      |
| 6   | **Upload report from memory** via `upload_bytes()` instead of writing a local `.md` file.                                            | `generate_markdown_report`      | Eliminates orphaned report file on disk.                                                             |
| 7   | **Scope `parsed_images/` per doc_id** (e.g. `parsed_images/{doc_id}/`) or use `BytesIO` for page PNGs.                               | V1 image extraction             | Prevents cross-task file collisions under concurrent ingestion.                                      |
| 8   | **Cache Docling `DocumentConverter`** as a singleton or module-level instance.                                                       | V2 pipeline                     | Avoids reloading ~500 MB–1 GB of ML models per document.                                             |
